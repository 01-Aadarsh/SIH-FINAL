## 1. Executive Summary

Ayurveda rests on a vast body of traditional knowledge — classical
formulations like Triphala churna, turmeric-based remedies, Ashwagandha
preparations — codified over centuries in recognized texts. Commercializing
or protecting an Ayurvedic innovation means navigating several overlapping
Indian and international legal regimes at once, and getting it wrong is
expensive:

- **Section 3(p) of the Patents Act, 1970** bars patenting an invention
  that is, "in effect, traditional knowledge" — a classical formulation
  cannot be monopolized by anyone. This protects the commons, but it also
  means a genuinely new innovation *built on* a classical base needs to
  clearly establish what's actually new about it, or risk a rejected (or
  wrongly-granted, later-challenged) patent application.
- **The Biological Diversity Act, 2002**, its **2023 Amendment**, and the
  **Biological Diversity Rules, 2024** require **prior approval from the
  National Biodiversity Authority (NBA)** before accessing an Indian
  biological resource commercially, transferring research results on one,
  or applying for a patent based on one — with **several different forms
  for several different situations**, not one universal form.
- Layered on top: **international treaties** (the WIPO Treaty on
  Intellectual Property, Genetic Resources and Associated Traditional
  Knowledge — "WIPO GRATK," adopted 2024; the Nagoya Protocol; the
  Budapest Treaty; the PCT) that apply differently from, and must never be
  conflated with, Indian domestic law.

A general-purpose AI chatbot is actively dangerous in this domain.
Independent evaluations of commercial "AI legal assistant" tools found
**17–33% hallucination rates** even when built on retrieval-augmented
generation — a wrong section number stated with total confidence is
worse than no answer, because it leads to real financial and legal
decisions made on false ground.

**IP-SAKTI Sahayak** is a source-cited AI co-pilot built specifically to
close this gap: it answers only from a fixed corpus of **30 real,
verified government/treaty documents**, attaches a **programmatic
citation** (document, page, section) to every claim — generated by code
from the actual retrieved text, never by the language model — and
**explicitly refuses to answer** ("I could not find this in my sources")
rather than guess when the corpus doesn't contain the answer. It keeps
Indian and international law strictly separate via an explicit
jurisdiction switch, classifies which of six regulatory categories a
formulation falls into, and points the user at the actual government
form (NBA/IPO) they likely need next — in text or voice, in multiple
languages.

## 2. Complete Architecture Matrix

| Layer | Technology | Engineering rationale |
|---|---|---|
| **Ingestion** | `pdfplumber`, custom hierarchical statutory chunker | Splits each of the 30 source PDFs so that, wherever a document has real "Section N / clause (x)" structure, each clause becomes its own citable chunk — not a slice of a fixed-size window that might cut a legal clause in half or bury it among unrelated text. |
| **Sparse retrieval (BM25)** | `rank_bm25` (BM25Okapi), domain-synonym-aware tokenizer | Exact keyword/section-number matching — dense embeddings alone miss precise legal terms. Same tokenizer used at index time and query time, with synonym normalization (e.g. "trademark" ↔ "trade mark") so a one-token difference doesn't silently break retrieval. |
| **Dense retrieval** | `sentence-transformers/all-MiniLM-L6-v2` (384-dim), pgvector on Postgres | Semantic/conceptual matching — catches a rephrased question that shares no exact words with the statute text. Jurisdiction-filtered at the SQL level, not post-filtered. |
| **RRF Fusion** | Reciprocal Rank Fusion (`1/(k+rank)`, k=60) | Fairly combines BM25 and dense results — a chunk ranking well on *both* signals rises to the top, rewarding agreement over either signal alone, rather than trusting one search method exclusively. |
| **Cross-Encoder Reranker** | `cross-encoder/ms-marco-MiniLM-L-6-v2`, calibrated `sigmoid(logit)` confidence | Re-scores the fused candidates for *actual* relevance (reads query and chunk together, not as separate embeddings) before anything reaches the LLM — this calibrated confidence is what powers the abstention decision. |
| **LangGraph DAG** | LangGraph, deterministic `StateGraph` | A fixed, traceable sequence (rewrite → triage → retrieve → rerank → generate → cite → enrich) with exactly one bounded conditional retry — never an open-ended autonomous agent loop, so every run's behavior is debuggable and reproducible. |
| **Formulation Triage** | Deterministic keyword classifier (no LLM call) | Classifies a question into one of 6 regulatory categories before generation, so the answer is framed with the right regulatory posture. Kept non-LLM deliberately — an LLM-driven classification here would reintroduce run-to-run non-determinism one step earlier than the system's own bounded retry already accounts for. |
| **Knowledge Graph** | Custom graph over statutory tags (`graph_kg/`), data-derived + reviewed cross-jurisdiction table | Surfaces real cross-jurisdiction pointers (e.g. a domestic Section 3(p) answer pointing at the WIPO GRATK Treaty's disclosure obligation) as a clearly separate "see also," never blended into the grounded answer itself. |
| **Form & Registry Navigator** | Deterministic catalog + keyword/tag matcher (`compliance/`) | Matches a question to the real NBA/IPO form it implies — form numbers verified against the actual indexed Biological Diversity Rules, 2024 text, not assumed. |
| **Generation (LLM)** | Groq (`AsyncGroq`), automatic multi-key rotation | Answers using *only* the retrieved context, never outside knowledge. Multi-key rotation automatically switches to a backup API key on a 429 (daily quota exhaustion) — a real failure mode this project hit during its own benchmark runs. |
| **Programmatic Citations** | Code-attached from retrieved chunk metadata | The single most load-bearing design decision: the LLM never writes a citation, so a citation cannot be hallucinated — it is always a real `source_file`/`page_number`/`section_heading` from a chunk that was actually retrieved. |
| **Sarvam ASR (Saaras)** | Sarvam AI speech-to-text | Converts a spoken question to text; validates file format/language before any network call; does not fail open (no reasonable fallback transcript exists), so a failure is a real, visible error rather than silent wrong output. |
| **Sarvam TTS (Bulbul)** | Sarvam AI text-to-speech | Speaks the *translated* answer in 11 of the languages translation supports — replaced an earlier Groq-based TTS implementation that was English-only and blocked on manual model-terms approval. |
| **Translation** | Sarvam AI, with a protected Ayurvedic-term lexicon | Question → English before retrieval, English answer → the user's language after generation. A fixed lexicon (Churna, Bhasma, Taila, Kwatha, Rasa Shastra, Asava, Arishta — Latin-script and Devanagari) is swapped for opaque placeholders before every translation call and restored after, so Sarvam never sees — and can't mistranslate or transliterate — these Sanskrit-derived pharmaceutical terms. |
| **Next.js UI** | Next.js 15, React 19, Tailwind | Jurisdiction toggle, live token streaming with automatic fallback, in-browser voice recording, clickable citations linking to the real source PDF, and dedicated panels for related provisions and actionable forms. |

## 3. Statutory Grounding Proof

### The 30 indexed documents

**24 India-jurisdiction documents** (`data/*.pdf`), including: Patents Act
1970, Patents (Amendment) Rules 2024, Trade Marks Act 1999, Copyright Act
1957, GI Act 1999 + GI Rules 2002/2025, Biological Diversity Act 2002 +
2023 Amendment + 2024 Rules, Drugs and Cosmetics Act and Rules, Drugs and
Magic Remedies (Objectionable Advertisements) Act 1954, NDCT Rules 2019,
National IPR Policy 2016, PPVFR Act 2001, Nutraceuticals Regulations, the
Ayurveda-Aahar FSSAI Gazette Notification, the Patent Office Manual of
Practice and Procedure, CTRI Registration Guidelines, the TKDL PIB
factsheet, and more.

**6 international-jurisdiction documents** (`data/international/*.pdf`):
the WIPO GRATK Treaty (2024, full text), the Nagoya Protocol (full text),
the Budapest Treaty (full verbatim article text — extracted directly from
WIPO Lex after the treaty's own PDF mirror went offline — plus WIPO's own
Secretariat summary note as a separate, distinctly-cited document), the
full Patent Cooperation Treaty text, and a WIPO IGC mandate-renewal
decision.

The authoritative, always-current list is `ls data/*.pdf` and
`ls data/international/*.pdf` — this dossier doesn't hand-maintain a copy
that can go stale.

### Hierarchical statutory chunking

For 11 of the 30 documents that have real "Section N. Title, clause (x)"
structure, a custom chunker (`ingestion/chunker.py`) makes **each
numbered/lettered clause its own citable chunk** — so Trade Marks Act
1999's Section 2(1)(zb) or Patents Act 1970's Section 3(p) are clean,
complete, individually-tagged chunks, not fragments buried inside an
arbitrary sliding text window alongside a dozen unrelated clauses.
Documents without this structure fall back to a plain sliding-window
chunker rather than being mis-parsed by a pattern that doesn't fit them.
Every chunk is validated at ingestion time to carry `source_file`,
`page_number`, `section_heading`, and `chunk_id` — ingestion fails loudly,
not silently, if any is missing, since every citation downstream depends
on it.

### How programmatic citations eliminate hallucination

The language model is given the retrieved text and instructed to answer
*only* from it — but the system does not trust the model to also report
its sources honestly. Instead, **`generation/citation.py`'s
`attach_citations()`** builds the citation list directly from the
metadata of the chunks the retrieval pipeline actually returned, entirely
in code, after generation completes. The model's own output is never
parsed for citation numbers or source names. A citation shown to the user
is therefore, by construction, always a real, retrievable, currently-
indexed document — **it cannot be a hallucination, because it never
passed through the part of the system capable of hallucinating.**

## 4. Feature Verification Showcase

### 1. Domestic vs. International Jurisdiction Switch

Verified live (`scripts/test_e2e_integration.py`, check (b)): a
`jurisdiction: "international"` question about the WIPO GRATK Treaty's
disclosure obligations returns citations exclusively from
`WIPO_GRATK_Treaty_2024.pdf` and `PCT_1970.pdf` — **zero** domestic Indian
Act citations mixed in. This isn't a prompt instruction the model might
ignore; jurisdiction is a hard partition at the retrieval layer itself
(a separate BM25 index per jurisdiction, built at ingestion time; dense
retrieval filtered at the SQL level) — international content is
architecturally unreachable from an `india`-jurisdiction query and vice
versa.

### 2. Formulation Triage Engine

Six categories — **Classical, Proprietary (P&P), Phytopharmaceutical,
Ayurveda-Aahar/Nutraceutical, Cosmetic, New/Non-Classical Drug** — assigned
by a deterministic keyword classifier (`graph/formulation.py`) before
generation, framing the answer with the correct regulatory posture (e.g.
a classical formulation gets framed around Section 3(p)/TKDL; a
proprietary one around genuine patentability and NBA approval). Detects
genuine ambiguity (keywords spanning 2+ categories) and surfaces a
clarifying question rather than silently guessing.

### 3. Compliance Form Navigator

Matches a question to the real official form it implies — verified
deterministically (`scripts/test_e2e_integration.py`, check (a); also
`backend/tests/test_forms.py`): the intent "I want to patent my Ayurvedic
formulation" reliably surfaces **NBA Form 7** (prior approval before
applying for IPR based on Indian biological resources — Biological
Diversity Act Section 6(1), Biological Diversity Rules 2024 Rule
16(1)(a)). This number was itself a real correction made during
development: an earlier draft assumed "Form 3," until checked directly
against the actual indexed Rules text. Other real, verified forms in the
catalog include NBA Form 2 (commercial access), NBA Form 3 (transfer of
research results), NBA Form 8 (Section 7 community/SBB route), and IPO
Form 18A (expedited patent examination, Rule 24C) — itself corrected from
an earlier assumption that conflated it with the unrelated "Form 8"
(mention-of-inventor) at the Patent Office.

### 4. Multilingual Voice Loop with Protected Sanskrit Lexicon

Speech in, speech out, via Sarvam's Saaras (ASR) and Bulbul (TTS) models,
verified live with a real audio round-trip during development (TTS
speech synthesized, fed back through ASR, transcript matched exactly).
Ayurvedic pharmaceutical terms — **Churna, Bhasma, Taila, Kwatha, Rasa
Shastra, Asava, Arishta**, in both Latin-script spelling variants and
Devanagari — are swapped for opaque numeric placeholders before every
Sarvam translation call and restored to their canonical English spelling
afterward, verified directly against the live API including a Devanagari
input ("भस्म" → placeholder → translated → restored to "Bhasma," never
"ash" or another lossy approximation).

### 5. Safe Abstention Guardrail

Verified live (`scripts/test_e2e_integration.py`, check (d)): an
adversarial, wholly out-of-scope query ("What is the capital of
France?") returns `flags.abstained: true`, an **empty** citations list,
and **zero** actionable forms attached — the system does not fabricate
sourcing or suggest irrelevant paperwork just because a question was
asked. The abstention marker is a fixed literal string
(`generation/prompts.py::ABSTENTION_MARKER`, "I could not find this in my
sources."), checked programmatically, never inferred from fuzzy text
matching.

```bash
cd backend

cp env.example.txt .env
# Fill in: DATABASE_URL (Neon/Supabase Postgres+pgvector), GROQ_API_KEY
```

`curl http://localhost:8000/health`.

### Frontend

```bash
cd frontend
npm install
cp .env.local.example .env.local
npm run dev
```
Verify: open `http://localhost:3000`.

### Multi-device / judge demo on another laptop or tablet

The backend already binds to `0.0.0.0` (`backend/run.py`) with CORS set
to `*` (`CORS_ORIGINS` in `.env`), so it's reachable from any device on
the same network at `http://<your-machine's-LAN-IP>:8000`. The one thing
to change: **`frontend/.env.local`'s `NEXT_PUBLIC_API_BASE_URL` must
point at that same LAN IP** (not `127.0.0.1`, which resolves to the
*viewing* device, not the host) before running `npm run dev` — find your
LAN IP with `ipconfig` (Windows) or `ifconfig`/`ip addr` (Mac/Linux).

### Answering tough questions

- **"How do you know it's not hallucinating?"** — Citations are attached
  by code from the chunks the retrieval pipeline actually returned; the
  language model's output is never parsed for citation text. Point at
  `generation/citation.py`.
- **"What if the AI model itself makes a mistake in wording?"** — The
  model is instructed to answer *only* from the retrieved context, and a
  post-generation check (`find_ungrounded_references`) flags any
  "Section N"-shaped claim in the answer that doesn't appear anywhere in
  the retrieved text, logged for review — an honest, additional check,
  not a claim of perfection.
- **"Why isn't accuracy 100%?"** — Point at Section 5 above and answer
  directly: real LLM-driven retry non-determinism, and one genuinely
  ambiguous trap query. Reproducibility and honest measurement, not a
  single inflated number, is the design philosophy.
- **"Does this work offline / if WiFi fails at the venue?"** — Yes:
  `OFFLINE_MODE=true` switches the LLM backend to a local Ollama model as
  an explicit operator flag for exactly this scenario.
- **"How is this different from just using ChatGPT?"** — ChatGPT (and
  general AI tools like it) answer from training data with no way to
  verify sourcing; independent evaluations found 17-33% hallucination
  rates on comparable "AI legal assistant" tools even with retrieval in
  place. This system's citations are structurally incapable of being
  fabricated, and it explicitly refuses to answer rather than guess.

## 8. Design Decisions — The Full Reasoning Behind Every Non-Obvious Choice

This section exists because "we used X" is a weaker answer than "we used
X instead of the more obvious Y, because Z happened when we tried Y."
Everything below is a real decision made during this project, not a
retroactive justification.

### 8.1 Retrieval architecture

**Q: Why hybrid BM25 + dense embeddings instead of just dense embeddings
(which is what most RAG tutorials use)?**
Legal text is full of exact tokens that *matter precisely* — "Section
3(p)," "Form 7," "Rule 24C." Dense embeddings are excellent at semantic
similarity ("turmeric" ≈ "curcuma") but can under-rank an exact,
rare-but-critical token match, because the embedding space optimizes for
overall meaning, not for "this one specific legal citation must match
exactly." BM25 is the opposite: exact-term matching, weighted so rare
terms count far more than common ones. Real legal questions need both.

**Q: Why Reciprocal Rank Fusion (RRF) specifically, instead of simply
concatenating both result lists or averaging raw scores?**
BM25 scores and cosine-similarity scores live on completely different,
incompatible numeric scales — averaging them directly would let whichever
score happens to have a larger numeric range silently dominate. RRF
sidesteps this by only using each list's *rank position* (`1/(k+rank)`),
which is scale-free — a chunk that's #1 on both lists always beats a
chunk that's #1 on only one, regardless of what the raw scores were.
`k=60` is a widely-used, empirically-stable default from the original RRF
paper; it wasn't re-derived from scratch for this specific corpus.

**Q: If fusion already ranks the results, why add a *third* step — the
cross-encoder reranker — on top?**
BM25 and dense embeddings both score a query against a chunk
*independently* of each other (compute an embedding/score for the query,
compute one for the chunk, compare). A cross-encoder reads the query and
the candidate chunk *together*, in one pass — a strictly more accurate
(if slower) way to judge "does this specific chunk actually answer this
specific question," which is why it runs last, on only the fused top-40,
rather than on the whole corpus (too slow to run on everything).

**Q: Why calibrate the reranker's output through a sigmoid instead of
using its raw score directly?**
The cross-encoder's raw output is an unbounded logit — informative for
*ranking* candidates against each other, but not directly interpretable
as "how confident is this, on a 0-1 scale" for a fixed decision threshold
like the abstention cutoff. Passing it through `sigmoid()` produces a
bounded, empirically-tested confidence: real on-topic queries scored
0.92-0.999, queries with no real answer in this corpus scored ~0.000 —
which is what makes a single fixed threshold (`RERANK_SCORE_THRESHOLD =
0.15`) a meaningful, sits-well-above-the-noise-floor decision boundary
rather than an arbitrary number.

**Q: Why does `FUSED_TOP_K` equal 40, a specifically odd-looking number,
and not the more common 20?**
This was raised from 20 after a real, reproduced regression: once
hierarchical statutory chunking made individual clauses short and
lexically sparse (see 8.2), the flagship "What does Section 3(p) say
about traditional knowledge?" query started abstaining — the correct
clause ranked BM25 #59 and dense #12 individually (both reasonable, just
not both in the combined top-20), so RRF's top-20 cutoff excluded it even
though it was clearly the right answer. Raising the pool to 40 was the
smallest tested value that fixed this specific, real, observed
regression — not pushed further, since a separate, harder query ("What is
a trademark?") would need pooling all the way to ~500 to reach its own
definition clause, and doubling-plus every query's reranking cost to
chase one already-marginal query wasn't judged worth it. That second gap
is left honestly documented as open, not silently patched over.

**Q: Why is jurisdiction enforced as a genuinely separate BM25 index per
jurisdiction, rather than one shared index filtered afterward?**
A shared-index-then-filter design means an international query could, in
principle, retrieve a domestic Indian Act chunk and then have it filtered
out *after* it already consumed a slot in the top-k — silently weakening
the effective search depth for exactly the queries that need it most, and
leaving open the possibility of a filtering bug leaking domestic content
into an international answer. Building one BM25Okapi index per
jurisdiction at ingestion time makes the separation structural: an
international-jurisdiction query is retrieving from an index that
*only ever contained* international documents in the first place.

### 8.2 Document processing

**Q: Why hierarchical statutory chunking instead of a simple fixed-size
sliding window (which is far simpler to implement)?**
A fixed-size window chunker can — and, tested directly, did — cut a
single legal clause across a chunk boundary, or bury a short, specific
clause (like Section 2(1)(zb)'s trademark definition) inside a 2000-
character window dominated by unrelated surrounding text, diluting its
retrieval signal. Making each numbered/lettered clause its own chunk
means a citation always points at *exactly* the clause it came from, not
an arbitrary slice that happens to contain it.

**Q: Why does the chunker fall back to the plain sliding-window approach
for some documents instead of hierarchical chunking for all 30?**
Because forcing a "Section N, clause (x)" parsing pattern onto a document
that doesn't actually have that structure produces *worse* results than
a plain window — false-positive section boundaries, or silently missed
content. The chunker only applies hierarchical parsing where it
statistically finds enough real section markers to trust the pattern
(`MIN_SECTIONS_TO_TRUST_HIERARCHICAL_PARSE`), and uses the plain,
well-tested fallback otherwise — matching the tool to what a specific
document actually looks like, rather than a one-size-fits-all rule.

**Q: Why does ingestion "fail loudly" (crash) instead of skipping a chunk
that's missing metadata?**
Every citation shown to a user is only as trustworthy as the metadata
behind it. A chunk silently missing `page_number` or `section_heading`
would produce either a broken citation or, worse, a citation quietly
defaulting to something generic — undermining the entire "every claim
traces to a real, specific location" guarantee. Failing the whole
ingestion run immediately makes a metadata gap something a human notices
and fixes before it ever reaches an answer, not something that erodes
trust silently in production.

### 8.3 Orchestration and safety

**Q: Why a fixed LangGraph DAG instead of a more flexible, autonomous
agent loop that could decide its own steps?**
An autonomous agent (one that can freely decide "search again," "call a
different tool," "reason some more," in any order, indefinitely) is
powerful but fundamentally harder to debug, audit, and reason about — and
for a domain where a judge, a legal reviewer, or a user might reasonably
ask "why did the system answer this way," an unpredictable step sequence
is a real liability, not a feature. A fixed DAG means every run follows
the exact same sequence of named steps, and any run's behavior can be
traced node by node.

**Q: Why exactly one bounded retry, and not zero, or unlimited?**
Zero retries means a single unlucky first-pass phrasing (one that happens
to score just below the confidence threshold) abstains on a question the
corpus genuinely could have answered — a real, avoidable false negative.
Unlimited retries reintroduces the unpredictability an autonomous agent
loop has, and risks a query looping indefinitely without ever reaching an
answer. One bounded retry is the smallest change that meaningfully
recovers from a bad first phrasing while keeping the DAG provably
terminating in a fixed number of steps.

**Q: Why is the formulation classifier a plain keyword matcher instead of
an LLM call, when an LLM would presumably classify more accurately?**
Because the system's own bounded-retry mechanism exists specifically to
compensate for LLM output not being perfectly reproducible run to run,
even at temperature 0. Using an LLM to classify formulation category
would reintroduce that exact same non-determinism *one step earlier*,
before retrieval even starts — meaning the same question could,
run to run, get triaged into two different categories and receive two
differently-framed answers. A keyword classifier is coarser, and will
misclassify genuinely ambiguous questions — but it gives the *same*
coarse answer every time, which is the property that actually matters
here more than raw classification accuracy.

**Q: Why is the knowledge-graph enrichment (`related_provisions`) also a
deterministic lookup rather than an LLM or agentic reasoning step?**
Same reasoning as the formulation classifier, applied to a second place
it was tempting to reach for an LLM: cross-jurisdiction pointers are
exactly the kind of "this is also relevant" judgment that benefits from
being the same answer every time a given set of statutory tags appears,
not a creative, re-derived-per-request judgment call.

**Q: Why does `attach_citations()` run entirely in code, with the LLM
never writing a citation?**
This is the single most important rule in the whole codebase, repeated
deliberately throughout the documentation rather than stated once and
assumed: if the language model is ever the one writing "Section 3(p),
page 12," there is no way to guarantee it isn't inventing a page number
that sounds plausible. By having code track which chunks were *actually*
retrieved and attach *their* real metadata after generation, a citation
is physically incapable of being a hallucination — not because the model
is well-behaved, but because the model's output is never consulted for
this information at all.

**Q: Why is there a separate post-generation check
(`find_ungrounded_references`) if citations are already guaranteed real —
isn't that redundant?**
It checks a different thing: not "are the citations real" (already
guaranteed by construction) but "did the model's own *prose* state a
specific section number that doesn't actually appear anywhere in the
text it was given" — i.e., did it slip a number in from its training
data despite being told not to. This is deliberately a diagnostic that
gets logged for a human to review, not an auto-editor that strips or
rewrites the sentence — surgically removing "Section 15" from a sentence
can leave ungrammatical nonsense with no reliable way to verify the
remainder still reads correctly, and this project's rule is "never edit
or generate a citation programmatically outside of `citation.py`'s own
real-chunk-metadata path."

**Q: Why is the abstention phrase a fixed literal string checked exactly,
instead of using the LLM's own judgment about whether it just said "I
don't know" in some paraphrased way?**
A fuzzy "does this sound like an abstention" check is itself a source of
false positives and negatives — the model could phrase uncertainty a
dozen different ways. A fixed, prompted marker string
(`ABSTENTION_MARKER = "I could not find this in my sources."`), checked
with a simple prefix match, makes "was this an abstention" a deterministic
question with one correct answer, not a judgment call layered on top of
an already-uncertain generation step.

### 8.4 LLM backend

**Q: Why Groq as the primary LLM provider instead of a well-known model
provider like OpenAI or Anthropic directly?**
Groq's inference hardware is built for speed, and offers a genuinely
usable free tier — both matter for a hackathon demo where latency and
cost both need to be low, without requiring a paid account to reproduce.
Nothing about the architecture is Groq-specific; `generation/llm_client.py`
is the only file that would need to change to point at a different
provider.

**Q: Why is local Ollama gated behind an explicit `OFFLINE_MODE=true`
flag instead of being tried automatically whenever Groq is slow or
unreachable?**
This was the *original* design — try Ollama first, fall back to Groq on
timeout — and it was changed after a real, measured problem: on the
development machine, Ollama's GPU path crashes outright (a CUDA driver
mismatch), forcing CPU-only inference measured at **~163 seconds** for
one grounded-generation call. Auto-trying Ollama first meant *every
single request* paid up to that delay before ever reaching Groq — not a
rare edge case, a tax on every request. `OFFLINE_MODE=true` turns this
into an explicit, deliberate operator decision ("I know the venue WiFi
is down, use the local model") rather than a per-request gamble the
system makes on your behalf.

**Q: Why automatic multi-key Groq rotation instead of just upgrading to a
paid tier?**
Multi-key rotation costs nothing extra (free-tier accounts) and solves
the actual problem this project hit directly: a single key's 200,000
token/day free-tier quota ran out mid-benchmark-run during this project's
own development and testing. A paid tier is also a reasonable fix, but
it requires a payment method and ongoing cost; automatic rotation across
a few free keys is a zero-cost mitigation for exactly the failure mode
that was actually observed, not a hypothetical one.

**Q: Why does rotation only trigger on a 429 (`RateLimitError`)
specifically, and not on any error?**
Rotating keys on a different kind of failure — a genuine network outage,
an authentication problem, a malformed request — wouldn't fix anything
(a different key won't help if the network itself is down), and would
burn through every configured key's connection attempt before finally
reporting the real underlying error, adding latency for no benefit. Only
a 429 specifically means "this key's quota is the actual problem,"
which is the one case rotation is actually the correct fix for.

### 8.5 Translation and voice

**Q: The problem statement explicitly names Bhashini — why is Sarvam AI
used instead?**
Sarvam AI was the provider with working, immediately-usable API access
during development; `api/translation.py`'s docstring says directly that
this is an interim choice and the swap to Bhashini (if/when a key becomes
available) touches only this one module — the rest of the pipeline never
sees a provider-specific detail, since translation happens only at the
two edges (question in, answer out) and retrieval/generation always
operate on English regardless of which provider translated it.

**Q: Why protect Ayurvedic terms with placeholder tokens instead of just
letting the translation model translate them directly?**
Because it was tested directly and found to be a real, reproduced
problem: translating "Bhasma" (a specific Ayurvedic pharmaceutical
preparation) without protection risked it coming back as a generic gloss
like "ash," losing the exact regulatory meaning used in the Drugs &
Cosmetics Act text this system cites. Swapping the term for an opaque
placeholder before translation means Sarvam's model never sees the word
at all, so it cannot mistranslate or transliterate something it never
received — verified directly against the live API in both directions,
including a Devanagari-script input.

**Q: Why did the placeholder format specifically need to be purely
numeric, rather than something more descriptive?**
Also a real, reproduced bug during development: an earlier alphabetic
placeholder format (e.g. `XPROTECTEDTERMX0X`) was itself treated by
Sarvam as an unrecognized English word and transliterated into Devanagari
nonsense, so the exact-string restoration step afterward never matched
and the mangled placeholder leaked straight into a real user-facing
answer. A purely numeric placeholder is recognized by the translation
model as a number, not a word, and survives untouched — confirmed by
testing several formats against the live API, not assumed.

**Q: Why was Groq's TTS replaced with Sarvam's Bulbul model?**
Two compounding, real problems with the original choice: Groq's TTS
model is English-only, so even working correctly it would read a
translated Hindi (or other-language) answer aloud in English — exactly
backwards for a multilingual product. Separately, the Groq account behind
this project never had that specific TTS model's usage terms accepted (a
manual step requiring org-admin console access), which blocked it from
working at all regardless of the language limitation. Sarvam's Bulbul
model, already integrated for translation, needed no new API key, no
manual approval step, and natively covers 11 real languages.

**Q: Why does speech-to-text (ASR) "fail closed" (raise a real error) when
translation and TTS both "fail open" (silently degrade)?**
Translation and TTS are both *enhancements* over an already-complete,
correct English pipeline — if either fails, there is a reasonable,
correct fallback already sitting right there (the original English text,
or no audio at all). Speech-to-text is different: it is the *only* source
of the question text in the voice-query flow. If it fails, there is no
reasonable text to substitute — silently returning an empty or guessed
transcript could send a completely different, unintended question into
the grounded pipeline without the user ever knowing their real question
was never actually asked. Raising a real, visible error is the honest
behavior here; pretending to have understood is not.

### 8.6 Compliance and corpus integrity

**Q: An earlier version of the form catalog said the NBA patent-approval
form was "Form 3" — why was that changed to "Form 7," and how is anyone
supposed to trust the new number either?**
The correction was made by checking the claim directly against the
actual, currently-indexed `Biological_Diversity_Rules_2024.pdf` text
(Rule 16(1)(a)) rather than trusting the original assumption — the same
standard this project applies to its own AI-generated answers is applied
to its own hardcoded reference data. The dossier and the code
(`compliance/form_navigator.py`'s own module docstring) document this
correction openly, by name, rather than silently fixing it and hoping
nobody asks — because "we checked and fixed our own mistake" is a more
trustworthy answer than a number with no visible history.

**Q: Why weren't the Biological Diversity (Amendment) Act 2023, the 2024
Rules, or the WIPO GRATK Treaty's text written out from general knowledge
to fill a gap sooner, when real source PDFs weren't yet available?**
Because doing so would be exactly the failure mode this entire system is
built to prevent: writing out specific section numbers and legal
provisos from an AI's own training-data recollection, then indexing that
text as if it were the authoritative statute, in a tool whose entire
value proposition is "never answer from anything but real, verified
source text." The moment real source PDFs became available for each of
these, the existing ingestion pipeline indexed them with zero code
changes — the wait was for real sourcing, not a technical limitation.

**Q: The Budapest Treaty's official PDF mirror was found to be dead during
development — why does the corpus have the real treaty text anyway
instead of just the WIPO Secretariat's summary note?**
Because the treaty's actual article text was still genuinely available —
just not as a standalone PDF anymore. WIPO Lex's own web page for the
treaty renders the full article text server-side as HTML (confirmed by
checking the raw page source directly, not assumed), so the real text was
extracted from that page and rendered into a PDF using a plain,
deterministic HTML-to-PDF conversion script — tag-stripping and
punctuation normalization only, with no AI involved in producing or
altering the substantive text. The Secretariat's note was *also* kept, as
a separate, distinctly-cited document, rather than merged with the treaty
text — a citation should always be able to say which of the two distinct
documents it actually came from.

### 8.7 Frontend

**Q: Why does the frontend try `/query/stream` (SSE) and fall back to the
plain `/query` endpoint, instead of just always using whichever one is
simpler?**
Streaming gives a visibly faster perceived response (tokens appear as
they're generated, rather than a single 20-90 second wait with no
feedback) — valuable for a live demo. But a live SSE connection is one
more thing that can drop mid-response (a network hiccup, a server
restart), and a user should never be left staring at a half-sentence with
no citations because of a transport-layer problem that has nothing to do
with whether the system could actually answer their question. Falling
back to the plain endpoint on any stream failure, and replacing the
partial text with the complete real answer, gets the reliability of the
simple approach with the responsiveness of the streaming one.

**Q: Why does picking a "formulation category" on the intake screen just
get folded into the question text, instead of being sent to the backend
as its own field?**
Because the backend genuinely has no such field — `formulation_category`
is always determined server-side, from the question's own text, by the
deterministic keyword classifier (see 8.3), specifically so the category
can't be spoofed or drift out of sync with what the question actually
says. Rather than silently dropping a UI control the user explicitly
interacted with, folding their selection into the outgoing question text
as a natural-language hint (e.g. "...regarding a classical formulation")
gives the classifier a genuine, real signal to work with — the control
does something true, instead of nothing.

**Q: `actionable_forms` and `related_provisions` were found attaching to
abstained or completely unrelated answers during development — what
happened, and is it actually fixed?**
Yes — this was a real bug caught by the offline evaluation benchmark, not
by review. `formulation_category` defaults to `"classical"` when no
category-specific keyword matches (a reasonable prior for this domain,
not itself a bug), but the actionable-forms matcher was, at the time,
also using that same default-prone category value as a trigger signal —
so a totally unrelated question like "what is the capital of France?"
would get default-classified as "classical" and then have an NBA form
attached to its abstention. The fix has two parts, both now covered by a
regression test that hits the real live pipeline
(`backend/tests/test_forms.py::test_run_query_attaches_no_forms_on_a_real_abstention`):
forms are never attached at all when the answer abstained, and the
matcher now uses the actual statutory tags carried by the specific chunks
that grounded *this* answer, not the coarser category-wide tag list.

### 8.8 Evaluation and honesty

**Q: Why run the automated test suite against the real live system (real
database, real Groq calls) instead of mocking everything, which would be
faster and cheaper?**
Because the properties this project actually needs to prove — that BM25
scores are bit-identical across repeated runs, that a specific real query
retrieves a specific real clause, that a real Sarvam translation call
protects a real Devanagari term correctly — are exactly the properties a
mock would have to *assume* rather than verify. A test suite that mocks
the retrieval layer could pass permanently while the real retrieval
silently regressed. The one deliberate exception is `test_asr.py`'s unit
tests, which mock Sarvam specifically because they're testing this
project's own request/response handling code, not Sarvam's transcription
accuracy — a narrower, correctly-scoped exception, not a general policy
of convenience.

**Q: Why publish a benchmark run showing 60% statutory accuracy instead
of re-running it until a better number comes up, or only publishing the
best run seen?**
Because the actual point of shipping an evaluation harness alongside the
product is *reproducibility* — anyone, including a skeptical judge, can
run `python scripts/evaluate_pipeline.py` themselves and see a real
number, not a cherry-picked one. Section 5 explains the two concrete,
identified reasons this specific run scored lower than an earlier one
(86.7%) rather than treating the variance as unexplained. A tool built
specifically to prevent confidently-wrong answers would be self-
defeating if its own accuracy claims weren't held to the same standard.
